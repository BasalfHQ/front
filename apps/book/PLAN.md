# B2B occupation & category pages — implementation plan

Build spec for the agent implementing the B2B SEO pages of the `book` app. Goal: one **highly specialized** landing page per bookable ESCO occupation — and one per category (15) — that sells Book (Basalf's booking app) to service providers — "Online booking for barbers", "Logiciel de réservation pour maçons"… B2C SEO (customers looking for a provider) is out of scope: there are no providers yet.

Read first: `front/CLAUDE.md` (app/ vs features/ rule), `front/apps/book/AGENTS.md` (Next.js version notes — read `node_modules/next/dist/docs/` before writing Next code).

## What already exists

- `packages/esco/data/booking-occupations.json` — 197 bookable occupations in 15 categories, labels per locale.
- `packages/esco/data/occupation-slugs.json` — `{ locale: { slug: occupationId } }`, generated by `packages/esco/scripts/generate_occupation_slugs.py` (run with `python3`). Slugs are translated per locale (`/for/beauty-wellness/barber`, `/fr/for/beaute-bien-etre/barbier`); the `/for` prefix is **not** translated. The script also writes `category-slugs.json` and fails if a category slug equals an occupation slug.
- `apps/book/src/lib/occupation-slug.ts` — `getOccupationIdBySlug(locale, slug)`, `getOccupationSlug(locale, id)`, `getOccupationSlugLocale(slug)`.
- Routes (`app/[locale]/(b2b)/for/`): `[category]` → `CategoryPage`; `[category]/[slug]` → `CategoryChildPage` (**occupation first**, else a category article); `[category]/[slug]/[article]` → `OccupationArticlePage`. Slug resolution in `features/b2b/resolve.ts`: a slug from another translation redirects to its locale (`/fr/for/beauty-wellness/barber` → `/en/for/beauty-wellness/barber`, prefix kept on purpose so the i18n middleware updates the `NEXT_LOCALE` cookie — without it the redirect loops); an occupation under the wrong category or at the old flat URL `/for/{occupation}` 308s to `/for/{category}/{occupation}`.
- CMS rendering: `features/blog/components/*` (text, list, faq, table, image, related, schema) render CMS slices; `Book.getPages(orgId)` / `Book.getPage(orgId, pageId)` fetch them.
- Locales: `en` (default, no prefix), `fr`. Domain: `https://book.basalf.com` (`lib/seo.ts#getBaseUrl`).

## Page anatomy

Occupation and category pages share one template (`features/b2b/landing-page.tsx`); a category page adds a "Find your trade" list (all its occupations, linked when live) after the hero and "Book for other trades" at the end instead of "Also for". Same template for every page, but the occupation-specific part must carry real, useful content — near-identical pages that only swap the H1 are doorway pages for Google and hurt the whole domain.

| # | Section | Source |
|---|---|---|
| 1 | Hero: H1 "Online booking for {occupation}" + occupation pain point + CTA | CMS (per occupation) |
| 2 | Example services for this occupation (name, duration, price) — shown as they would appear on a Book profile | CMS (per occupation) |
| 3 | **Your profile page** — screenshot of a public provider page (`/service-provider/[orgId]`) + explanation: customers see your services and book in a few clicks | Shared |
| 4 | **Your bookings** — screenshot of the reservations list in the `slot` app (`apps/slot/src/features/reservations`) + explanation | Shared |
| 5 | **Your availability** — screenshot of the slots list in the `slot` app (`apps/slot/src/features/slots`) + explanation | Shared |
| 6 | Why Book: **really simple to use** and **really cheap — €5/month**, **multiple services** per provider | Shared |
| 7 | Occupation-specific FAQ (3–5 questions) | CMS (per occupation) |
| 8 | "Also for": 5–8 sibling occupations from the same category | Generated from `booking-occupations.json` |
| 9 | Final CTA → signup (checkout in the `base` app, see below) | Shared |

Shared sections (3–6, 9): texts in the app's i18n messages (en + fr), screenshots as static files under `apps/book/public/b2b/` (`profile.png`, `bookings.png`, `slots.png`). Screenshots are supplied by the user — use clearly marked placeholders until then. Where the occupation fits naturally, weave its name into shared copy ("Your barber profile page…") so shared blocks still read as specialized.

Per-page sections (1, 2, 7): one CMS page per occupation / category and locale, written through the Basalf CMS MCP. Convention: CMS page `url` = `/{enSlug}` — occupation (`/barber`) or category (`/beauty-wellness`) English slug; locale-independent key, one page per locale; one CMS "folder" per landing page, see Articles — `seo.title/description` → page metadata + hero, slices in order: `description` (hero pitch), `table` (example services), `faq`. Render with the existing blog slice components.

CMS access (which org, token) is handled by the user through a lib — out of scope, don't implement or ask about it. Keep all CMS reads behind one helper in `features/b2b` (e.g. `getOccupationContent(locale, occupationId)`) so it can be wired to that lib later.

## CMS content brief (SEO)

The template is shared; the CMS page is what makes each page rank. Every page written through the CMS MCP follows this:

- **`seo.title`** ≤ 60 chars, keyword first, brand last: "Online booking for barbers — €5/month | Book" / "Logiciel de réservation pour barbiers — 5 €/mois | Book". Unique per page.
- **`seo.description`** 140–160 chars: what the occupation's clients can book + "€5/month, everything included" (fr: "5 €/mois, tout compris"). Unique per page.
- **Slices, in this order:**
  1. `description` — hero pitch, 1–2 sentences, speaks the trade's language (a real pain point of that trade, not a generic one).
  2. `table` — 4–8 typical services of the trade: `[name, duration, price]` rows ("Haircut", "30 min", "25 €"). Realistic market values; shown as the phone mockup **and** as an indexable table.
  3. Guide — `heading` (level 2, becomes the section title) then `text` / `list` / `heading` (level 3) slices: 300–600 words specific to the trade (how clients book that trade today, no-shows, walk-ins, session lengths, seasonality…). This is the part that stops the pages being doorway pages — never reuse it across occupations.
  4. `faq` — 4–6 questions a professional of that trade asks before signing up; answers 2–4 sentences, answer first.
- **Category pages** (`/{categoryEnSlug}`): same slices, pitched to the whole category ("Online booking for beauty & wellness pros"). `table` mixes typical services from several of its trades; the guide covers what the trades of the category share (and where they differ), naming them. Never a copy of one occupation's page.
- **Never:** free trial, invented statistics or testimonials, claims about features Book doesn't have, keyword stuffing, "TTC/VAT".
- **Locale:** write each locale natively (not a translation of the other); fr uses the generic masculine plural ("les barbiers").

### Articles brief

- Answers one real question a professional of that trade searches (no-shows, pricing a service, managing walk-ins, first clients…), 800–1500 words, answer in the first paragraph.
- `seo.title` = the question/answer, not "Book"; `seo.schemas`: one `article` schema (date, readingTime, keywords).
- Slices: `heading` (2/3) + `text` + `list` / `table`, optional `faq`, end with a `related` slice to the landing (`/{enSlug}`) and 1–2 sibling articles.
- Never a second landing page in disguise: an article targeting "booking software for barbers" competes with `/for/beauty-wellness/barber`.
- **Category articles** (`/{categoryEnSlug}/{article-slug}` → `/for/{categorySlug}/{article-slug}`) share the URL space with occupations: an article slug must **never** be an occupation slug (any locale) — the occupation always wins and the article is never served. Check `occupation-slugs.json` before creating one.

## Signup CTA

Every CTA (hero + final) links to the checkout page of the `base` app: `${baseUrl}checkout` for `en`, `${baseUrl}fr/checkout` for `fr` — `baseUrl` from `@repo/config` (`https://basalf.com/` in prod, `http://localhost:3000/` in dev); route lives in `apps/base/src/app/[locale]/(checkout)/checkout/`. Plain `<a>`, it's another app.

Key selling points — hammer them everywhere (hero, shared sections, FAQ, CTA):

- **Really simple to use** — set up your services and slots in minutes, no training, nothing to configure.
- **Really cheap** — **€5/month** (fr: 5 €/mois), all features included. Keep it that plain, no VAT/TTC mention. In code the price comes from `features/b2b/pricing.ts` (`BOOK_PRICE`, `formatPrice`, `{price}` in messages); CMS content is plain text, so it spells the price out.
- **Multiple services** per provider.

No free trial — never mention one.

## Indexing rule

An occupation or category page is **live only when its CMS page exists for that locale**. Otherwise → `notFound()` (keep the cross-locale redirect). Only live pages go into the sitemap and into "Also for" / hub links. Content is published progressively: first 20–30 high-value occupations (hairdresser, barber, beautician, physiotherapist, coach, tattoo artist…), more later based on Search Console data.

## Internal linking

- `/for` hub page: 15 categories with their live occupations. Linked from the header logo and the footer. The home page (`app/[locale]/page.tsx`) is **not** a B2B page: keep it as is, no B2B layout, never link to it from `/for` pages.
- Category pages: `/for/{categorySlug}`, parent of their occupations (`/for/{categorySlug}/{occupationSlug}`). An occupation belongs to exactly one category. `/for` lists every category with a live page or live occupations.
- Breadcrumbs: Home › Trades › {Category} › {Occupation}; the category crumb only when its page is live in that locale. Occupation pages link to their category page from "Also for".
- Internal links always target the final URL, never a URL that redirects.
- Articles live in their occupation's folder (topical silo): CMS url `/{enSlug}/{article-slug}` → public `/for/{categorySlug}/{occupationSlug}/{article-slug}` (`/fr/for/beaute-bien-etre/barbier/{article-slug}`; the article slug is the same in every locale, lowercase-kebab). An article is live only when its occupation landing is live in that locale. The landing lists all its articles ("Guides for barbers"); each article links back to the landing (breadcrumb + CTA box) and to 3 more articles of the folder. A `related` slice may point to other CMS urls (`/barber`, `/hairdresser/some-article`, `/beauty-wellness`): rendered as links when live.

## SEO

- `generateMetadata` lives in `page.tsx` (only exception to "app/ is routing only"): title, description from CMS `seo`, canonical, `alternates.languages` built from the occupation **id** via `getOccupationSlug` (slugs differ per locale).
- JSON-LD: `SoftwareApplication` (offers: 5 EUR/month), `FAQPage` from the faq slice, `BreadcrumbList`; `ItemList` of linked pages on category pages and `/for`.
- `sitemap.ts`: `/for`, live category and occupation pages and their articles, with hreflang alternates.
- Prefer static generation + revalidate over `force-dynamic` for these pages.

## Code layout

- `app/[locale]/(b2b)/for/page.tsx`, `for/[category]/page.tsx`, `for/[category]/[slug]/page.tsx`, `for/[category]/[slug]/[article]/page.tsx` — thin: params → feature component, plus `generateMetadata`.
- `features/b2b/` — `LandingPage` (shared template), `OccupationPage`, `CategoryPage`, `ForHubPage`, article pages, `resolve.ts` (slug dispatch/redirects), `content.ts` (CMS reads), category audience labels in messages `b2b.audience.{categoryId}`, shared sections as components (`components/profile-section.tsx`, `bookings-section.tsx`, `slots-section.tsx`, `pricing-section.tsx`, `also-for.tsx`, `breadcrumbs.tsx`), CMS fetch helpers.
- `lib/occupation-slug.ts` — extend for category slugs and sibling lookup.
