# B2B occupation pages — implementation plan

Build spec for the agent implementing the B2B SEO pages of the `book` app. Goal: one **highly specialized** landing page per bookable ESCO occupation that sells Book (Basalf's booking app) to service providers — "Online booking for barbers", "Logiciel de réservation pour maçons"… B2C SEO (customers looking for a provider) is out of scope: there are no providers yet.

Read first: `front/CLAUDE.md` (app/ vs features/ rule), `front/apps/book/AGENTS.md` (Next.js version notes — read `node_modules/next/dist/docs/` before writing Next code).

## What already exists

- `packages/esco/data/booking-occupations.json` — 197 bookable occupations in 15 categories, labels per locale.
- `packages/esco/data/occupation-slugs.json` — `{ locale: { slug: occupationId } }`, generated by `packages/esco/scripts/generate_occupation_slugs.py` (run with `python3`). Slugs are translated per locale (`/for/barber`, `/fr/for/barbier`); the `/for` prefix is **not** translated.
- `apps/book/src/lib/occupation-slug.ts` — `getOccupationIdBySlug(locale, slug)`, `getOccupationSlug(locale, id)`, `getOccupationSlugLocale(slug)`.
- `apps/book/src/app/[locale]/(b2b)/for/[occupation]/page.tsx` → `features/b2b/index.tsx` (`OccupationPage`): placeholder that renders the slug, 404s on unknown slugs, and redirects a slug from another translation to its locale (`/fr/for/bricklayer` → `/en/for/bricklayer`, prefix kept on purpose so the i18n middleware updates the `NEXT_LOCALE` cookie — without it the redirect loops).
- CMS rendering: `features/blog/components/*` (text, list, faq, table, image, related, schema) render CMS slices; `Book.getPages(orgId)` / `Book.getPage(orgId, pageId)` fetch them.
- Locales: `en` (default, no prefix), `fr`. Domain: `https://book.basalf.com` (`lib/seo.ts#getBaseUrl`).

## Page anatomy

Same template for every occupation, but the occupation-specific part must carry real, useful content — near-identical pages that only swap the H1 are doorway pages for Google and hurt the whole domain.

| # | Section | Source |
|---|---|---|
| 1 | Hero: H1 "Online booking for {occupation}" + occupation pain point + CTA | CMS (per occupation) |
| 2 | Example services for this occupation (name, duration, price) — shown as they would appear on a Book profile | CMS (per occupation) |
| 3 | **Your profile page** — screenshot of a public provider page (`/service-provider/[orgId]`) + explanation: customers see your services and book in a few clicks | Shared |
| 4 | **Your bookings** — screenshot of the reservations list in the `slot` app (`apps/slot/src/features/reservations`) + explanation | Shared |
| 5 | **Your availability** — screenshot of the slots list in the `slot` app (`apps/slot/src/features/slots`) + explanation | Shared |
| 6 | Why Book: **really simple to use** and **really cheap — 5 €/month**, **multiple services** per provider | Shared |
| 7 | Occupation-specific FAQ (3–5 questions) | CMS (per occupation) |
| 8 | "Also for": 5–8 sibling occupations from the same category | Generated from `booking-occupations.json` |
| 9 | Final CTA → signup (checkout in the `base` app, see below) | Shared |

Shared sections (3–6, 9): texts in the app's i18n messages (en + fr), screenshots as static files under `apps/book/public/b2b/` (`profile.png`, `bookings.png`, `slots.png`). Screenshots are supplied by the user — use clearly marked placeholders until then. Where the occupation fits naturally, weave its name into shared copy ("Your barber profile page…") so shared blocks still read as specialized.

Per-occupation sections (1, 2, 7): one CMS page per occupation and locale, written through the Basalf CMS MCP. Convention: CMS page `url` = `/for/{enSlug}` (locale-independent key, one page per locale), `seo.title/description` → page metadata + hero, slices in order: `description` (hero pitch), `table` (example services), `faq`. Render with the existing blog slice components.

CMS access (which org, token) is handled by the user through a lib — out of scope, don't implement or ask about it. Keep all CMS reads behind one helper in `features/b2b` (e.g. `getOccupationContent(locale, occupationId)`) so it can be wired to that lib later.

## Signup CTA

Every CTA (hero + final) links to the checkout page of the `base` app: `${baseUrl}checkout` for `en`, `${baseUrl}fr/checkout` for `fr` — `baseUrl` from `@repo/config` (`https://basalf.com/` in prod, `http://localhost:3000/` in dev); route lives in `apps/base/src/app/[locale]/(checkout)/checkout/`. Plain `<a>`, it's another app.

Key selling points — hammer them everywhere (hero, shared sections, FAQ, CTA):

- **Really simple to use** — set up your services and slots in minutes, no training, nothing to configure.
- **Really cheap** — **5 €/month**, all features included. Keep it that plain: just "5 €/month", no VAT/TTC mention.
- **Multiple services** per provider.

No free trial — never mention one.

## Indexing rule

An occupation page is **live only when its CMS page exists for that locale**. Otherwise → `notFound()` (keep the cross-locale redirect). Only live pages go into the sitemap and into "Also for" / hub links. Content is published progressively: first 20–30 high-value occupations (hairdresser, barber, beautician, physiotherapist, coach, tattoo artist…), more later based on Search Console data.

## Internal linking

- `/for` hub page: 15 categories with their live occupations. Linked from the home page (`app/[locale]/page.tsx`, empty today) and the footer.
- Category hubs: `/for/category/{categorySlug}` (dedicated segment so it never collides with occupation slugs; category slugs translated like occupations — extend the Python script).
- Breadcrumbs on every occupation page: Home › For › {Category} › {Occupation}.
- Internal links always target the final URL, never a URL that redirects.
- Blog articles (later, via CMS) link contextually to occupation pages; occupation pages may list 2–3 related articles.

## SEO

- `generateMetadata` lives in `page.tsx` (only exception to "app/ is routing only"): title, description from CMS `seo`, canonical, `alternates.languages` built from the occupation **id** via `getOccupationSlug` (slugs differ per locale).
- JSON-LD: `SoftwareApplication` (offers: 5 EUR/month), `FAQPage` from the faq slice, `BreadcrumbList`.
- `sitemap.ts`: add `/for`, category hubs and live occupation pages with hreflang alternates.
- Prefer static generation + revalidate over `force-dynamic` for these pages.
- Switch the cross-locale redirect to `permanentRedirect` before launch.

## Code layout

- `app/[locale]/(b2b)/for/page.tsx`, `for/[occupation]/page.tsx`, `for/category/[category]/page.tsx` — thin: params → feature component, plus `generateMetadata`.
- `features/b2b/` — `OccupationPage`, `ForHubPage`, `CategoryHubPage`, shared sections as components (`components/profile-section.tsx`, `bookings-section.tsx`, `slots-section.tsx`, `pricing-section.tsx`, `also-for.tsx`, `breadcrumbs.tsx`), CMS fetch helpers.
- `lib/occupation-slug.ts` — extend for category slugs and sibling lookup.
